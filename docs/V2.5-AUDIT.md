# Oliveira DevCloud v2.5 — Auditoria pré-implementação

> Executada antes de qualquer código da v2.5, conforme protocolo solicitado. Esta auditoria cobre o
> estado real do repositório v2.4 (não o que a documentação afirma), os comandos executados, os bugs
> pré-existentes encontrados e corrigidos (necessários para obter um baseline verde), e o plano de
> implementação da v2.5 (Regression Intelligence + Merge Risk Report).

## 1. Arquitetura encontrada

Monorepo npm workspaces (`apps/*`, `packages/*`), sem build tool de monorepo (sem Turborepo/Nx) —
orquestração é só `npm run <script> --workspaces --if-present`.

```
apps/
  api/      Fastify control-plane (ESM, tsx em dev, tsc+node em prod)
  web/      Next.js 16 (App Router, Turbopack)
  worker/   BullMQ workers (orquestração de agentes + provisionamento assíncrono)
packages/
  database/                 Prisma schema + client (schema único, sem multi-schema)
  workspace-engine/         Ciclo de vida Docker dos workspaces
  terminal-engine/          tmux + docker exec TTY
  ide-engine/                code-server via proxy
  agent-engine/              Codex/Claude em tmux dentro do workspace
  git-engine/                 Git worktrees por agente (isolamento)
  orchestrator-engine/        DAG de steps (AGENT/SYSTEM), fila BullMQ
  review-engine/              Review worktree (`review/<orchestrationId>`), merge de branches de agentes, gates
  secret-manager/             AES-256-GCM para secrets
  setup-engine/ setup-queue/  Provisionamento assíncrono (clone, install, IDE, portas)
  command-center-engine/      Planner determinístico/OpenAI/Anthropic -> DAG
  repository-intelligence/    Mapa de arquivos/árvore/manifests via docker exec (cache por commit SHA)
  code-intelligence/          Símbolos/endpoints/edges locais (regex-based, sem AST real)
  context-engine/             Seleciona contexto focado por objetivo (scoring lexical)
  task-context-router/        Contexto por agente (Codex backend, Claude frontend)
  dependency-router/          Adiciona dependsOn quando há contrato produtor/consumidor forte
  contract-intelligence/      Endpoints HTTP produtores/consumidores (regex-based) + issues
  contract-gate/              Compara baseline x candidato de contratos, bloqueia regressões HIGH
infra/
  workspace-images/node/      Imagem Docker dos workspaces de usuário
  nginx/, production/         Nginx + Dockerfiles + compose de produção
docs/                          V0.2 .. V2.4, ARCHITECTURE.md
```

### Fluxo de Review & Merge atual (v2.4)

```
Codex/Claude terminam (branches em worktrees isoladas)
        -> git.snapshot() de cada worktree (commit de segurança)
        -> reviews.prepare(): cria worktree `review/<id>`, faz merge --no-ff de cada branch de agente
        -> roda gates permitidos (npm test/build/lint/typecheck) na worktree de review
        -> re-analisa contratos HTTP na worktree de review (contract-intelligence)
        -> contract-gate compara baseline (branch principal) x candidato (worktree de review)
        -> reviewStatus = CONFLICT | GATE_FAILED | READY
        -> aprovação humana (ADMIN/OWNER) com optimistic concurrency (reviewBaseCommit == HEAD atual)
        -> merge --no-ff da worktree de review na branch principal
```

Ponto de integração exato para a v2.5: `apps/api/src/routes/orchestrations.ts`, handler
`POST /:id/review/analyze` (linhas ~73-125). Contract Gate já roda ali, depois dos quality gates. É
o lugar natural para Regression Intelligence (mesmo padrão: baseline recomputada antes do merge,
candidato analisado na `review.reviewPath`).

`Orchestration.reviewSummary` é `Json?` — já guarda `{ ...result, contractGate, ready }`. A v2.5 vai
estender esse mesmo objeto com `regressionIntelligence`, sem quebrar o formato existente (o front-end
lê campos individuais, não faz parsing estrito).

### Cache de intelligence (padrão a reutilizar)

`RepositorySnapshot`, `CodeIntelligenceSnapshot`, `ContractIntelligenceSnapshot` — todas
`@@unique([workspaceId, commitSha])`, só cacheiam quando `git status` está limpo (`revision.clean`).
Os helpers em `apps/api/src/lib/*IntelligenceCache.ts` seguem o mesmo padrão de ~5 linhas. A v2.5 não
precisa de uma nova tabela de snapshot: a baseline é recomputada a partir dos snapshots já cacheados
de Repository/Code/Contract Intelligence (branch principal) e o candidato é sempre recalculado contra
a worktree de review (nunca cacheado, pois review worktrees são efêmeras e o objetivo é refletir
exatamente o que será mergeado — ver Fase 13 do prompt original).

## 2. Estado real antes desta sessão

- **Não é repositório git** (`git status` -> "not a git repository"). Isso é o diretório de trabalho
  raiz do projeto; não afeta o Regression Intelligence em si, que opera via `docker exec` dentro dos
  *workspace containers* dos usuários (que têm seu próprio `.git`), não neste diretório.
- `node_modules` não existia — nunca houve `npm install` nesta máquina.
- Nenhum workspace tinha script `test` real (raiz roda `npm run test --workspaces --if-present`, mas
  nenhum `package.json` define `test`). Idem para `lint`. Ou seja, os "quality gates" de CI
  (`.github/workflows/ci.yml`) rodam `typecheck` e `build` apenas — não há suíte de testes no
  projeto todo antes desta sessão.
- `npm run build`/`npm run typecheck` **nunca haviam sido executados com sucesso**: havia 6 bugs
  independentes que impediam qualquer um dos dois de terminar (detalhados abaixo). Isso indica que o
  código evoluiu via edição direta, sem rodar `tsc` nem `next build` para validar.

### Achados registrados mas não corrigidos (fora do escopo necessário para a v2.5)

- **Conflito de porta local**: esta máquina tem um PostgreSQL nativo (`postgres.exe`, serviço Windows)
  e um Memurai (`memurai.exe`, compatível com Redis) já ocupando `5432`/`6379`. O `docker-compose.yml`
  do projeto usa esses mesmos mapeamentos de porta (correto para uma máquina limpa). Para validar
  ponta a ponta nesta máquina específica, subi containers isolados em portas alternativas
  (`55432`/`56379`) só para o teste, sem alterar o `docker-compose.yml` do projeto — não é um bug do
  projeto, é uma particularidade desta máquina de desenvolvimento.
- `infra/production/Dockerfile.api` / `Dockerfile.worker` fazem `RUN npm run build -w @oliveira/api`
  sem antes buildar os pacotes internos (`packages/*`) dos quais a app depende — o mesmo problema de
  ordenação encontrado no `npm run build --workspaces` local (contornado aqui rodando duas vezes).
  Recomendação para v2.6: `RUN npm run build --workspaces --if-present` antes do build do app, ou
  adotar um orquestrador de build com grafo de dependências (Turborepo/Nx).
- Não existe suíte de testes no projeto (nenhum workspace define `test` real). A v2.5 introduz os
  primeiros testes reais do projeto, escopados ao novo pacote.
- `2 moderate severity vulnerabilities` reportadas por `npm audit` (dependências transitivas,
  `cron-parser@4`/`uuid@10` deprecados) — não relacionadas à v2.5, não bloqueantes.

## 5. Riscos técnicos para a v2.5

1. **Regex-based intelligence, não AST real.** `code-intelligence` e `contract-intelligence` usam
   regex para extrair símbolos/endpoints. Regression Intelligence herda essa limitação: falsos
   negativos são possíveis (símbolo renomeado de um jeito que o regex não captura). Mitigação: seguir
   o mesmo princípio conservador do Contract Gate — só bloquear com evidência forte, warning para o
   resto.
2. **Baseline vs candidato vêm de fontes diferentes.** Baseline é cacheada por `commitSha` da branch
   principal (pode estar em cache de execução anterior); candidato é sempre recomputado ao vivo na
   `review.reviewPath` (nunca em cache, pois é uma worktree efêmera). Preciso garantir que a baseline
   usada é exatamente a mesma capturada pelo Contract Gate no mesmo `review/analyze` (reaproveitar a
   mesma chamada, não recalcular separadamente).
3. **Sem tabela de cache dedicada para Regression Intelligence.** Decisão: não criar nova migration/
   tabela nesta fase — o relatório é determinístico e barato o suficiente (reaproveita snapshots já
   cacheados) para recomputar a cada `review/analyze`, e é persistido dentro do `reviewSummary` (Json)
   existente do `Orchestration`, igual ao Contract Gate. Reduz risco de mais uma migration numa área
   onde a v2.4 já tinha uma pendente quebrada (bug #13).
4. **RBAC.** O endpoint novo (`GET /orchestrations/:id/regression-report`) precisa seguir exatamente o
   padrão de `requireOrgRole` já usado em todas as rotas de orchestration — carregar a organização a
   partir do `workspace.project.organizationId` do orchestration, nunca aceitar `organizationId` vindo
   do cliente.

## 6. Plano de implementação

1. `packages/regression-intelligence` (`@oliveira/regression-intelligence`) — tipos fortes
   (`RegressionReport`, `BaselineMetrics`/`CandidateMetrics`, `Changes`, `RegressionFinding`) e
   scanners puros (sem I/O) que recebem `RepositoryIntelligence`/`CodeIntelligence`/
   `ContractIntelligence` de baseline e candidato (já providos pelo caller) — mantém o pacote
   determinístico e testável sem Docker.
2. Detectores: `TEST_REMOVED`, `ENDPOINT_REMOVED` (via `ContractGateResult` já calculado),
   `SYMBOL_REMOVED`, `CRITICAL_MODULE_CHANGED`, `TEST_COVERAGE_RISK`, `MIGRATION_RISK`,
   `DEPENDENCY_CHANGE`, `CONFIG_CHANGE` — cada um em função pura própria.
3. Risk Engine separado (`calculateRisk(findings, gateSignals) -> { score, level, blocking }`),
   pesos e cap em 100, regras de bloqueio conservadoras (Contract Gate BLOCK, testes/build/lint
   falhando, conflito Git => score mínimo fixo, nunca por heurística fraca de símbolo).
4. Integração em `orchestrations.ts` `/review/analyze`: depois do Contract Gate, computar
   `RegressionReport` reaproveitando `baselineContracts`/`candidateContracts` já calculados +
   `repositoryIntelligence`/`codeIntelligence` de baseline e candidato; anexar a
   `reviewSummary.regressionIntelligence`; `reviewStatus` passa a considerar `blocking` do risk
   engine além do Contract Gate.
5. `GET /api/v1/orchestrations/:id/regression-report` — reaproveita o mesmo `reviewSummary` já
   persistido (não recomputa), com `requireOrgRole`.
6. UI: novo card "Merge Risk" na página `/orchestrations`, mobile-first (cards/accordion, sem tabela).
7. Testes com `node:test` (nativo, sem dependência nova) para Risk Engine e cada detector.
8. `docs/V2.5.md`, atualização do `README.md`, bump `2.4.0 -> 2.5.0` nos `package.json` coerentes.
