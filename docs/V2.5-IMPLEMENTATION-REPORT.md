## 3. Migrations

Ver `docs/V2.5-AUDIT.md` §3, bug #13. Nenhuma migration nova foi necessária para a v2.5 em si — o relatório de regressão é persistido em `Orchestration.reviewSummary` (campo `Json?` já existente), o mesmo padrão que o Contract Gate já usa. A única mudança em `packages/database/prisma/migrations/` foi a reconstrução do histórico quebrado, pré-requisito para `prisma migrate dev` funcionar (confirmado rodando do zero contra Postgres real).

## 4. Testes adicionados

30 testes novos em `packages/regression-intelligence/src/__tests__/` (Vitest, mesmo runner usado por `apps/api/src/lib/auth.test.ts` e `packages/secret-manager/src/index.test.ts`, que já existiam no repo em paralelo a este trabalho):

- `detectors.test.ts` (16) — um ou mais casos por detector: `TEST_REMOVED` (nada removido / poucos / muitos), `ENDPOINT_REMOVED` (consumido/não consumido), `SYMBOL_REMOVED` (exportado público / não-exportado / inalterado), `CRITICAL_MODULE_CHANGED` (1 arquivo / 3+ arquivos, migrations excluídas), `TEST_COVERAGE_RISK` (com/sem teste relacionado), `MIGRATION_RISK`, `DEPENDENCY_CHANGE` (nomeada/lockfile-only), `CONFIG_CHANGE` (alto/baixo impacto)
- `riskEngine.test.ts` (9) — thresholds de nível, soma/cap de score, cada sinal de bloqueio mínimo (Contract Gate/build/test/conflito), MEDIUM isolado não bloqueia, finding `blocking:true` força bloqueio, lint isolado não afeta score
- `index.test.ts` (5) — relatório fim-a-fim: diff limpo é LOW/não-bloqueante, split regressions/warnings por severidade, endpoint consumido removido bloqueia fim-a-fim, conflito de git bloqueia, `changes` reflete corretamente adds/removes de arquivo/endpoint/symbol

Não há teste de integração contra Postgres/Docker reais para o Regression Intelligence (documentado como limitação/próximo passo em `docs/V2.5.md`) — os scanners e o Risk Engine são puros por design exatamente para permitir teste unitário determinístico sem infraestrutura.

```
npm run db:generate   → exit 0
```

- `npm run dev -w @oliveira/api` → `/health` e `/ready` respondendo `ok`, `/api/v1/system` consultando o banco de verdade

- `next build` completo (17 rotas) prerenderiza sem erro, incluindo `/orchestrations`, `/ide` e `/terminal` (as duas últimas tinham bugs de SSR pré-existentes, corrigidos)

## 6. Erros ainda existentes / não corrigidos nesta sessão

- 2 vulnerabilidades moderate do `npm audit` (`uuid` via `dockerode`) — fix exige upgrade breaking do `dockerode`, usado em 8 pacotes; não arriscado sem uma janela de regressão dedicada.
- Nenhum workspace define `lint` de verdade (script existe e roda, mas é sem-op em todos os `package.json`) — fora do escopo da v2.5, mas é uma lacuna real do projeto.
- `infra/production/Dockerfile.api`/`.worker` não buildam `packages/*` antes do app (mesma causa-raiz do bug de ordenação do CI) — não testado neste ciclo por não ter sido exercitado (não há pipeline de deploy real ainda).

## 7. Riscos e limitações

Ver `docs/V2.5.md` §"Limitações conhecidas" (MIGRATION_RISK nunca escala para HIGH sem conteúdo de diff; DEPENDENCY_CHANGE só cobre o `package.json` raiz; detecção de símbolo é regex, não AST) e `docs/V2.5-AUDIT.md` §5 (riscos técnicos identificados antes de codificar).

## 8. Recomendações para v2.6

1. Plumbing do conteúdo real do diff de migrations para permitir `MIGRATION_RISK: HIGH` com evidência (hoje deliberadamente sempre MEDIUM).
2. Testes de integração do fluxo completo `review/analyze → regression-report` contra Postgres real.
3. `infra/production/Dockerfile.*` buildando `packages/*` antes do app correspondente.
4. Resolver as 2 vulnerabilidades moderate do `dockerode`/`uuid` numa janela dedicada de regressão.
5. TypeScript project references entre os `packages/*`, eliminando a necessidade do "duplo build" no CI/local para popular `.d.ts` entre pacotes internos.
